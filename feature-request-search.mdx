## Introduction

### Purpose

This document describes a feature that adds a free search box to documentation products that are deliberately left out of the built-in Mintlify search. It covers the problem, the proposed approach, the assumptions behind it, and the requirements, screens and user stories needed to build and accept it.

### Problem Statement

The documentation site holds five products in one repository, served as a single Mintlify site with a product switcher. Mintlify's built-in search works for only one of them. Management decided that the other products must not appear in that search, and their pages carry `noindex`, so they are also absent from Google. As a result, readers of these products have no way to search within the documentation and must browse the navigation or guess page names.

The solution must cost nothing to run, must not change the `noindex` setting, and must not require a separate search page, because readers should search from inside the existing documentation pages. The team already pays for Meilisearch Cloud and wants an option that avoids a paid or self-hosted server.

### Summary of Proposed Approach

Build a static search that runs in the reader's browser, fed by an index that GitHub builds automatically from the `.mdx` files.

1. A GitHub Actions workflow runs on every push to a product's branch. It reads every `.mdx` file in that product's folder, removes frontmatter, code blocks and component tags, splits each page into sections by heading, and writes one JSON index file per product.
2. The workflow saves each index file to a branch named `search-index` in the same repository.
3. A single script, `search.js`, placed in the docs root, loads on every Mintlify page. On pages of the configured products it adds a search box at the top of the page, loads all product indexes, merges them, and searches them in the browser.
4. Results are grouped by page. Each product gets a fair share of the visible results, so a large product cannot crowd out a smaller one.

Options that were considered and set aside:

- **Pagefind:** cannot be used, because Mintlify builds and hosts the HTML and no build output is available to index.
- **Self-hosted Meilisearch:** needs a server, and the free cloud tiers reviewed require a card or are time-limited trials.
- **Moving to Docusaurus, Starlight or Nextra:** a full migration, out of proportion to the need.
- **One combined index file built by a single workflow:** harder, because the product folders live on different branches and one failed build would block every product.

### Assumptions

- The repository is public, so the index branch can be read through `raw.githubusercontent.com` without authentication.
- The page content is already public. The pages are hidden from search engines with `noindex`, not protected by access control, so a public index file adds no new exposure.
- Each product has a long-lived branch (for example `ai-for-service-dev` and `ai-for-work-dev`) and a folder with the same name as its URL prefix.
- Content reaches the live site by merging to `main`. If anyone pushes straight to `main` without going through the product branch, the workflow must also watch `main`.
- Mintlify loads any `.js` file in the docs folder on every page, so one script can serve all products.
- Mixing AI for Service and AI for Work results in one search is acceptable to management. This is listed as an open question below and should be confirmed.
- GitHub Actions is enabled, and workflow permissions can be set to read and write.

## Requirements Specification

### Summary

| Area | Requirement in brief |
| - | - |
| Coverage | Search box on every page under `/ai-for-service/` and `/ai-for-work/`, including the two landing pages without a trailing slash |
| Scope of results | Results from all configured products, each result labelled with its product |
| Result quality | One result per page, with section links, ranking by relevance, highlighted matches |
| Convenience | Recent searches, keyboard shortcut, light and dark mode support |
| Freshness | Index rebuilt automatically on every relevant push |
| Cost and hosting | No paid service and no server |
| Isolation | No search box on products that are not configured |

### Functional Requirements

| ID | Requirement | Priority |
| - | - | - |
| FR-1 | Show a search box at the top and center of the page on every page of a configured product, and on no other page. | Must |
| FR-2 | The box shows a search icon and the placeholder text "Search...". | Must |
| FR-3 | Search results appear in a dropdown under the box as the reader types. | Must |
| FR-4 | Every word typed must match somewhere in a section for it to be returned. | Must |
| FR-5 | Group results by page. Show the page title, the best-matching section, and a text snippet. Show up to 8 pages. | Must |
| FR-6 | Show up to 3 other matching sections of the same page as small links that open the section directly. | Must |
| FR-7 | Rank whole-word matches in titles and headings above matches in body text, and rank pages with more matches higher. | Must |
| FR-8 | Search all configured products together and label each result with its product name. | Must |
| FR-9 | Reserve a fair share of the visible results for each product, so one product cannot fill all slots. | Should |
| FR-10 | Show matched words in green, semi-bold text, with a lighter green in dark mode. | Should |
| FR-11 | When the box is empty and focused, list the last 5 searches. Selecting one runs it again. A Clear link removes the list. | Should |
| FR-12 | Save a search to the recent list when the reader presses Enter or opens a result. | Should |
| FR-13 | Ctrl+Shift+K (Cmd+Shift+K on Mac) moves the cursor into the box. Esc closes the dropdown. | Could |

| FR-15 | Hide the Mintlify Preview Widget (file-changes icon at the bottom right) on the pages where the script runs, controlled by one setting. | Could |
| FR-16 | Adding a product requires only a new workflow file and one new entry in the product list in `search.js`. | Must |

### Index Build and Automation Requirements

| ID | Requirement |
| - | - |
| IR-1 | A workflow runs on every push to the product branch that changes a file in the product folder, and can also be started by hand. |
| IR-2 | The build reads every `.md` and `.mdx` file in the folder and removes frontmatter, imports, comments, component tags, images, fenced code blocks and Markdown symbols. |
| IR-3 | Each page is split into sections at second and third level headings. Each section record holds the page title, heading, URL with anchor, and text, with section text capped at 2,000 characters. |
| IR-4 | The workflow publishes one JSON file per product to the `search-index` branch, creating the branch on the first run. |
| IR-5 | Workflows for different products run one at a time, so they do not collide when writing to the same branch. |
| IR-6 | New, edited and deleted pages are all reflected after a rebuild, because the full index is regenerated each time. |
| IR-7 | The build script lives under `.github` with a `.cjs` extension, so Mintlify does not load it as a page script. |

### Non-Functional Requirements

- **Cost:** zero. No paid search service, server or database.
- **Privacy:** no search terms are sent anywhere. Recent searches stay in the reader's own browser.
- **Freshness:** a change appears in search within about 5 minutes of the workflow finishing, limited by GitHub's file caching.
- **Performance:** the index loads the first time the reader clicks in the box. The AI for Service index is about 5.9 MB (7,878 sections) and the AI for Work index is about 0.3 MB (392 sections), so the first search on a slow connection can take a moment.
- **Compatibility:** works with Mintlify's page navigation without a full reload, in light and dark mode, and on desktop, tablet and phone widths.
- **Security:** result text is escaped before display, so page content cannot inject markup into the results.

### User Stories

#### [Story #1](https://koreteam.atlassian.net/browse/XOP-6579): Search box on product pages

As a documentation reader, I want a search box on the pages of the product I am reading, so that I can find a topic without browsing the navigation.

Acceptance criteria:

- The box appears on every page under `/ai-for-service/` and `/ai-for-work/`, including the landing pages `/ai-for-service` and `/ai-for-work`.
- The box shows a search icon and "Search...".
- The box does not appear on pages of any other product.
- The box stays correct when the reader moves between pages without a full reload.

#### Story #2: Results grouped by page

As a reader, I want each page to appear once with links to its matching sections, so that one page does not fill the whole result list.

Acceptance criteria:

- A search for "MCP" lists each matching page once, not once per section.
- Up to 8 pages are shown, and up to 3 other matching sections appear under each page as links.
- Selecting a section link opens that page at the section.
- Pages with the word in the title or heading rank above pages that mention it only in the body.

#### Story #3: Search across products with a product label

As a reader, I want results from both AI for Service and AI for Work, so that I find the right page even when I start from the wrong product.

Acceptance criteria:

- A search from an AI for Service page returns AI for Work pages, and the reverse.
- Each result shows a label with its product name.
- The same search returns the same results from either product's pages.
- A product with many matches cannot take all 8 slots when another product also has matches.
- If one product's index cannot be loaded, results from the other product are still shown.

#### Story #4: Recent searches

As a reader, I want to see my recent searches, so that I can repeat a search quickly.

Acceptance criteria:

- Clicking into the empty box shows up to 5 recent searches, newest first.
- A search is saved when I press Enter or open a result. A repeated search moves to the top and is not duplicated.
- Selecting a recent search fills the box and shows its results.
- Clear removes all recent searches.
- Recent searches are stored only in my browser.

#### Story #5: Readable matches

As a reader, I want matched words to stand out, so that I can see why a result was returned.

Acceptance criteria:

- Matched words in snippets and section links are green and semi-bold, with no background color.
- The green is dark enough to read on a light page and lighter on a dark page.

#### Story #6: Index stays current automatically

As a documentation owner, I want the search index to rebuild whenever content changes, so that I do not maintain it by hand.

Acceptance criteria:

- A push that changes a file in a product folder starts the workflow and ends with a green run.
- The product's JSON file on the `search-index` branch is updated.
- New, edited and deleted pages are reflected in search within about 5 minutes.
- Two product workflows that finish at the same time do not fail each other.

#### Story #7: Add another product

As a documentation owner, I want to add search to another product without rebuilding the solution, so that coverage can grow later.

Acceptance criteria:

- Adding a product needs a copy of the workflow with the branch, folder and file name changed.
- Adding a product needs one new entry in the product list in `search.js`, with its name, URL prefix and index address.
- No change is needed to the search logic or styling.

#### Story #8: Clean page for readers

As a reader, I want a page without the Mintlify preview file-changes icon, so that the page looks like a finished site.

Acceptance criteria:

- The Preview Widget button at the bottom right is hidden on pages where the script runs.
- One setting in `search.js` turns the hiding on or off.

### Out of Scope

- Search for products that are not configured, and any change to the `noindex` setting.
- Searching text inside code blocks. These are left out of the index to keep it small.
- Access control or private documentation. The index file is public, like the pages.
- A separate search page.
- Typo tolerance, synonyms and language-specific search.

### Dependencies and Risks

| Item | Detail | Mitigation |
| - | - | - |
| Mintlify page script behavior | The search relies on Mintlify loading `search.js` on all pages and on its page layout. A Mintlify change could affect placement. | Check the box after Mintlify updates. Placement is controlled by one CSS rule. |
| Public index file | The index contains page text and can be read by anyone who has the address. | Confirm the content is not confidential. The pages themselves are already public. |
| Index size | The AI for Service index is about 5.9 MB, which slows the first search on slow connections. | Shorten the stored text per section if the delay becomes a complaint. |
| Workflow permissions | The workflow needs read and write permission to create the `search-index` branch. | Set workflow permissions in repository settings, with an organization admin if needed. |
| Deploy branch | The index is built from the product branch. Content on that branch but not yet on the live site could appear in search. | Build the live index from `main`, or merge product branches before content goes out. |
| Preview Widget | The widget is hidden with CSS only. It is still present in the page. | If the changed-file list must not be public, change the Mintlify preview setting. |
